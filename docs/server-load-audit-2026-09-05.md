# KOAN / CLE 通信負荷調査（2026-09-05）

対象は調査時の未コミット変更を含む作業ツリー。実装の変更は行っていない。大学サーバーへのリクエスト、実アカウントの操作、負荷試験は実施せず、コード・合成応答・ローカルブラウザテストで確認した。

## 1.5.0での対応（同日）

以下は調査後の実装変更。下記以外の調査結果は、修正前の記録として残す。

- 実行中のKOAN認証確認を共有し、同時20要求を1通信にまとめる。CLEも同じタブの認証確認を共有する。完了結果のキャッシュや追加の待機は導入していない。
- 掲示走査の100ページ目・時間割の4ページ目で、結果に使わない次ページを要求しない。取得・解析する範囲は従来どおり。監査の「101リクエスト」はジャンル内100リクエストへ減る（ルート取得は別）。100ページより先へ進めない問題そのものは未解決。
- 掲示の時間制限・通信失敗・構造異常でも、それまで解析した掲示と完了済みジャンルを返して保持する。失敗理由と一部取得状態を残し、完了済みジャンルの取り直しを防ぐ。未完了ジャンル内の先頭からの走査は継続する。
- 既存のキャッシュ期間、自動・手動更新頻度、通常更新の並列数、ページ数・時間制限は維持する。
- KOAN認証待ちの通信間隔は、UXへの影響を確認したうえで1秒から5秒に変更した。ログイン済みの初回確認は即時、タブを閉じたことのローカル検出は1秒間隔を維持する。

修正後の確認：型チェック、ユニットテスト137件、ビルド、差分の空白チェックが成功。`tests/server-load.e2e.ts` と `tests/sync-experience.e2e.ts` の計24件も成功した。新しい検証には合成DOM・応答のみを使い、外部通信を遮断した。大学サーバーでの検証は行っていない。

KOAN認証待ちの変更後は、即時応答・90秒待機の合成条件で確認が91回から19回になる。認証完了の検出は最大約4秒余計に遅れる。通常更新の直列化やサーバー待機指定による再試行延期は、この変更には含めていない。

## 調査時点の結論

通常時はキャッシュ、画面間の排他、失敗時の待機が機能する。ただし、KOANは**認証待ちの高頻度ポーリング、通常取得の同時実行、大量掲示の再巡回**に改善余地があり、「十分に低負荷」とはまだ評価できない。

CLEは取得単位の並列制限・再試行制限がKOANより整っているが、利用科目数に応じた通信と障害時の追加通信は発生する。冗長構成や実際のサーバー余力は今回確認していない。リクエスト数だけでCPU・DB負荷や障害への寄与は判断できない。

## 調査時点で優先した改善箇所

### 1. KOAN：ログイン待ちで約1秒ごとにポータルを取得する

- 根拠：`public/background.js` の `probeKoanLogin`（265行付近）、`ensureKoanLogin`（752行付近）。
- 初回のポータル確認に失敗するとログインタブを開き、90秒の間、1秒待機してポータルを再取得する。待機中の確認にもHTML全体のGETとリダイレクト追従を使う。
- 合成時計と即時の未認証応答で、**90秒に91回の確認**を再現した。実際は各応答時間が加わるため回数は減るが、認証リダイレクトやタブのページ読み込みは別途発生する。
- 通信障害・503等も `ok: false` にまとめるため、障害時にこの認証待ち経路へ入る可能性がある。同期全体の指数バックオフは、この1回の認証処理の内部を抑制しない。
- 最初の確認は `koanLoginTask` の共有判定より前なので、別経路から同時に認証を要求すると初回確認も重複し得る。
- 改善案：未認証と通信障害を区別し、障害時は認証開始を止める。認証画面の遷移・完了通知を主体にし、補助ポーリングは段階的に間隔を延ばして回数を制限する。初回確認も共有する。

### 2. KOAN：通常更新が最大5系統を同時取得し、全経路共通の通信間隔制限がない

- 根拠：`src/koan.ts` の `fetchHtml`（202行付近）、`refreshLight` の `Promise.all`（1460行付近）。
- 時間割、履修、休講・補講、アンケート、掲示を同時開始する。合成応答を保留する実行で**同時5件**を再現した。
- 8週間分の休講・補講は最大8ページを待機なしで順次取得する。時間割の月送りにも固定の待機はない。750msの待機は主に掲示の巡回だけに適用される。
- Web Locksは同期ジョブ同士の排他であり、1ジョブ内の通信を直列化しない。掲示リンクの検索、認証確認、タブ内の成績取得もすべてを覆う共通制御にはなっていない。
- 改善案：KOAN全経路を対象に、端末内で同時1件・開始間隔を設ける。キャッシュ表示はそのまま使い、画面操作を待たせずに通信だけを順番に進める。間隔の具体値は大学側の指針や受動的な応答時間の観測に基づき調整する。

### 3. KOAN：未完了の掲示ジャンルは先頭から読み直し、進捗なしの再巡回になり得る

- 根拠：`src/koan.ts` の `fetchGenre`（1645行付近）、`refreshSnapshot`（1695行付近）。
- 完了済みジャンルの再取得は省ける。しかし、未完了ジャンルのページ位置は保存せず、既知の掲示を識別しながら先頭から通過する。
- 「12ページ」は新しい掲示を含むページの上限であり、再開時の総リクエスト数の上限ではない。通過する既知ページは最大100ページの走査枠を消費する。
- 先頭100ページが既知で、101ページ目以降にも続く未完了ジャンルを合成すると、**101リクエスト・100ページ解析・新規0件・未完了**になった。最後に取得した101ページ目はループ終了で解析されない。同じ状態から再試行しても先へ進まない。
- 3分制限の例外がジャンルの途中で発生した場合、その呼び出し内で集めた掲示も返却されず、次回に同じ範囲を取り直す。1回ごとは終了するが、再試行を繰り返すと無駄な通信が続く。
- 改善案：未完了ジャンルの進捗と途中結果を保存する。セッション付きURLを恒久保存する設計は避け、位置を復元できる条件を確認する。進捗がない再試行は待機を延ばし、未解析ページの先読みをなくす。

### 4. KOAN：サーバー指定の待機時間と取得部分ごとの障害抑制が不足する

- KOANの直接取得・タブ経由取得はHTTPエラーを一般的な例外に変換し、`Retry-After` を再試行制御に反映しない。バックグラウンド側がヘッダーを返してもKOAN側は利用しない。
- 通常更新の各取得が失敗しても警告付きで返り、`LIGHT_FAILURE_KEY` は削除される。ポータル成功・5系統失敗の合成実行でこれを確認した。
- アプリ全体では、`src/App.tsx` が警告を失敗として扱い、`src/sync.ts` が自動再試行の間隔を2、4、8…最大64分へ延ばしていた。したがって、調査時点のUIが30秒ごとに失敗先へ通信していたわけではない。
- ただしKOAN全体を止める粗い制御になっており、取得部分ごとに失敗先を休ませる保証や、大学側から指定された待機を守る保証はない。
- 改善案：429/503と待機ヘッダーを保ち、共通の通信制御に反映する。部分取得ごとに失敗状態を保持し、成功部分の更新と切り分ける。

## 正常時の通信量の目安

以下は1端末・ログイン済み・取得成功・自動同期有効・画面表示中のコード上の件数。リダイレクト、認証画面、公式タブのHTMLや静的ファイル、ユーザーが開く本文は含めない。実測のサーバー負荷ではない。

| KOANの処理 | 間隔・件数 |
| --- | --- |
| キャッシュがすべて新しい | 大学への通信なし。30秒ごとの処理はローカル判定 |
| 新着掲示・今週の授業変更 | 約10分ごとにポータル確認1＋変更1＋掲示1＝3件 |
| 当月時間割・アンケートも期限切れ | 約30分ごとに上記へ2件追加＝5件 |
| 8週間分の再確認 | 6時間ごと。変更は1ページから8ページへ増え、時間割も月送り分が加わる |
| 履修科目 | 24時間ごとに1件追加 |
| 成績 | 6時間ごとに認証確認1＋2画面のGET/POST計4＝5件。必要なら公式タブの読み込みが追加 |
| 全ジャンル掲示・初回 | ルート1＋11ジャンル×最大12ページ＝最大133件、別に認証確認。750ms間隔・3分制限で少なくなる場合あり |
| 全ジャンル掲示・新着なし | 完了済みの巡回は6時間ごと。各ジャンルが1ページで終わるならルート込み12件、すべて既知で2ページずつ確認するなら23件。別に認証確認 |
| 手動の通常更新 | 直近1分を再利用。連打は抑制するが、毎分押し続ければ短期情報への確認は毎分可能 |

長期項目の更新がない1時間を継続表示する場合、通常更新は概算 **3×6＋2×2＝22件/時**。成績、掲示全体、長期項目の更新はこれに加わる。利用者全体では端末数に応じて増えるため、この平均値だけで安全とは判定できない。

## CLEの評価

- 課題10分、メッセージ通常15分、コース24時間、連絡事項は科目ごと2時間のキャッシュがある。
- 課題状態は通常1回最大6件、連絡事項は最大4科目。取得ワーカーは主に3並列。メッセージは1回8ページ、同期全体には120秒の制限がある。
- JSON取得は同一タブ・URLの実行中処理を共有し、再試行は最大2回。認証エラーは通常のHTTP再試行対象から外す。待機には乱数を加え、`Retry-After` を参照する。
- ただし、3並列は全通信を合算した制限ではない。課題取得とメッセージ取得は重なる。履修科目の課題一覧は科目ごとの通信があり、コース数・ページ数に応じて増える。
- `Retry-After` なしの再試行はおおむね0.5〜0.75秒、次に1〜1.5秒と短い。長い `Retry-After` は即時再試行では考慮するが、永続的な失敗記録では最大1時間へ丸める箇所がある（`src/cle.ts:431`、連絡事項の失敗処理も同様）。長時間の停止要求を厳密には守れない。
- 資料はユーザー操作時に取得し6時間キャッシュする。ただしファイル名調査には最大200 URLへのGET（3並列、本文キャンセル）や資料画面の巡回があり、全資料保存などの明示操作時は通常同期より通信が増える。
- 優先順位はKOANの認証と巡回の修正が先。その後、CLEにも全通信共通の並列上限と長い待機指定の保持を適用する。

## 確認と限界

- 関連ユニットテスト：6ファイル・100件成功（KOAN、CLE、同期、認証、KOANタブ通信、バックグラウンド契約）。
- ローカルE2E：7件成功。キャッシュ中の再読み込み・連打、期限切れ部分だけの取得、成績・掲示の自動同期、非表示・オフライン停止、完了済み掲示ジャンルのスキップ、複数タブの成績取得共有、失敗後の再読み込み・フォーカス復帰をまたぐ待機を確認。
- 追加の合成ハーネス：認証確認91回、通常取得の同時5件、部分失敗時の取得層の失敗記録消去、100既知ページからの進捗なし再巡回を確認。実コードを抽出またはTypeScriptから変換して実行し、時計・fetch・DOMを合成した。大学への通信は行っていない。
- サーバーの冗長構成、同時利用者数、応答量、DB処理時間、実運用のアクセスログは未確認。実環境では通常の1回の利用中に、本文・Cookie・認証情報・セッションURLを保存せず、件数・時間・HTTPステータスのみ集計すれば検証できる。実際のサーバー余力の判断には管理者側の観測が必要。
